    I am honored to be invited to an interview for a Y Combinator-backed company—RevisionDojo (YC F24) When I walked into the office, I felt like a high schooler in a group of elite engineers. Even as a developer myself, being a community college student in that "builder vibe" was a little bit intimidating, but it felt inspiring.  The interview was a reflection of me. My task was to build a feature within a set time. It was a very engaging, appealing, and challenging task for a builder. Using AI accelerated my development massively, but it also led to complete chaos. Ironically, prototyping had never been faster, yet I'd never been more lost. I had learned a lesson about technical debt: I have to understand the flow and logic behind the code without sacrificing speed. I spent the bulk of my time on system architecture and flow design. Then I realized I had become reliant on AI to handle the logic. As the code base grew more complex, there were fallbacks, functions, and parts I couldn't understand; there was no way back. It resulted in a presentation that lacked polish and confidence. I was more than happy to be given such an invaluable opportunity. As a self-taught builder, I believe there is still a massive learning curve ahead of me. So, given this opportunity, I know what I am capable of and what I have to focus on. Massive thank you to Michael Tong and RevisionDojo (YC F24).

    Today, I learned about two design patterns: DTO and DAO. DTO (Data Transfer Object) is a pattern that serves as a pathway for data to move from one layer of an application to another. It helps structure and control how data is passed around. DAO (Data Access Object), on the other hand, abstracts database interactions. It’s where you can place logic related to data access, keeping it separate from other parts of the application. One key advantage is flexibility. With DAO, switching between ORMs becomes much easier. Considering we had to move from Prisma to Sequelize during our capstone project, I can only imagine how much more complex that transition would have been in a large-scale application without such a pattern in place. This made it clear why DTOs and DAOs are especially valuable in larger systems where structure, scalability, and maintainability matter more.     GTM vibecoding update: Goodbye Supabase. Hello, Railway. Why I'm switching. I used Supabase because bolt.new made the setup dead simple. And it was. But as I scaled, Supabase's pricing got out of sync with the value it creates. It charges for 3 things: 1. Platform 2. Usage (multiple types–functions, bandwidth, other stuff I didn't care enough to learn) 3. Add ons (don't think I use these–but maybe?) For the skyp ai marketing site, it was great to get it set up. Built into Bolt, super fast. I have edge functions running to connect a beehiiv with the site so we get more SEO juice (not something you can do with Substack, to my knowledge). See Tyler Denk 🐝 there's a cool behiiv feature that isn't related to dashboards 😎 Supabase has limitations–no proper server infrastructure. But it works for what I was doing. Or I made it work. Setup was a breeze. Using Supabase I built a powerful progressive capture signup form that would have cost $100/mo on Typeform. Edge functions do a lot in the background–newsletter stuff, qualification stuff. It does what I need it to and was (basically) free. Until I vibecoded 2 other projects.
